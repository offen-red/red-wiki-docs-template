# /decision — 결정을 남긴다

원천 파일이 없는 지식이 하나 있다. **"왜 그렇게 정했나."** 회의와 대화에서만 나오고, 안 적으면 석 달 뒤에 같은 논의를 처음부터 다시 한다. 그때 나오는 말은 늘 같다 — "그거 전에 얘기했었는데."

`/ask` 는 문서에 있는 것을 답하고, `/draft` 는 문서를 쓰고, **여기는 대화에서만 나오는 것을 붙잡는다.** 위키에 대화가 남는 유일한 길이다.

**기록이 본체다. 문서 반영은 별개의 일이고, 별개로 묻는다.** 결정은 "그때 그렇게 정했다" 는 사실이지 "지금 문서가 이렇다" 는 뜻이 아니다. 둘을 붙여 놓으면 반영할 수 없는 때에 결정을 안 남기게 되는데, 그러면 이 스킬이 잡으려던 것을 정확히 놓친다.

닿는 문서는 **찾아서 보여준다**(3번). 고칠지는 사람이 정한다. 반영을 미뤄서 결정과 제품 문서가 어긋나 있는 동안은 `/ask` 가 그 사실을 알린다 — **현재 기준은 늘 제품 문서**이고 결정은 "왜·언제·누가"를 답한다.

## 결정이 아닌 것

|                                           | 왜 아닌가                                                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 아직 논의 중인 것                         | 결정은 **닫힌 것**이다. "그렇게 하는 게 나을 것 같은데" 는 아직 열려 있다                                                                   |
| 사실·정의                                 | 그건 `product/` 나 용어집이다. 결정은 "우리가 고른 것"이지 "원래 그런 것"이 아니다                                                          |
| 작업 지시                                 | "이거 만들어 줘" 는 결정이 아니라 할 일이다                                                                                                 |
| 코드 레포 안의 기술 결정(ADR)             | red-wiki 는 명사만 담는다(CLAUDE.md 2절). 그 레포의 `.claude/` 로 간다                                                                      |
| **red-wiki 자체를 어떻게 굴릴지 정한 것** | 이 위키는 **red 서비스** 지식을 담는다. 앱·스킬·규약 결정은 규칙이 사는 파일(`.claude/`)과 `docs/ops/` 에 적고, 경위는 커밋 메시지에 남긴다 |

**애매하면 묻는다.** "지금 정하신 건가요, 아니면 아직 보는 중인가요?" 논의를 결정으로 굳혀 두면 다음 사람이 그걸 근거로 움직인다.

마지막 줄이 특히 새기 쉽다. red-wiki 를 만지는 대화에서 이 스킬을 부르게 되기 때문이다. 판별선은 하나다 — **"red 제품이 없어져도 이 결정이 의미가 있나?"** 예면 여기가 아니다.

## 여섯 칸

자유 서술로 받지 않는다. **요약하게 두면 "왜"를 가장 먼저 잃는다.**

| 칸                | 없으면                                                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **무엇을 정했나** | 한 문장. 없으면 결정이 아니다                                                                                                                             |
| **왜**            | 이게 본체다. **이유 없는 결정은 다음 사람이 뒤집는다**                                                                                                    |
| **버린 대안**     | 대안과 **그 이유**를 같이. 검토 안 했으면 "검토 안 함"이라고 적는다. 비워 두면 그 대안이 반드시 다시 올라온다                                             |
| **누가·언제**     | 결정자·참여자와 날짜. 날짜는 추측하지 말고 확인한다                                                                                                       |
| **영향**          | `registry.yaml` 의 시스템 id, 문서 경로, 코드 경로 + **되돌리기 비용**(낮음/중간/높음). **3번에서 실제로 찾는다** — 여기서 받는 것은 사용자가 아는 범위다 |
| **재검토 조건**   | 어떤 상황이 되면 이 결정을 다시 보나. 이 위키는 결정을 고치지 않고 `supersedes` 로 뒤집으므로, **뒤집을 시점이 결정 안에 적혀 있어야** 놓치지 않는다      |

**여섯을 넘기지 않는다.** 칸이 늘면 아무도 안 채운다.

**모르는 칸은 지어내지 않는다.** 사용자에게 묻고, 그래도 안 나오면 `❓확인 필요` 로 남긴다. 특히 **"왜" 를 대화에서 추측해 채우지 않는다** — 그 문장이 나중에 결정의 근거로 읽힌다.

## 안 받는 칸

아직 안 정해진 것은 **Notion 태스크**가 관리한다(기한·담당·상태). 여기는 확정된 것만 담는다.

| 안 받는 것            | 왜                                       |
| --------------------- | ---------------------------------------- |
| 상태                  | 결정은 닫힌 것이라 `status` 가 늘 `완료` |
| 결정 필요일           | Notion 태스크가 가져간다                 |
| 후보안 목록           | **버린 대안**에 흡수                     |
| 평가 기준 · 논의 요약 | **왜**에 흡수                            |
| 결정할 사항(질문형)   | 제목이 명사형이면 중복                   |

## 절차

### 1. 결정이 맞는지 확인한다

위 표로 거른다. 사용자가 `/decision` 을 직접 불렀으면 결정으로 본다.

### 2. 이미 있는 결정을 찾는다

`docs/decisions/` 를 훑어 **같은 것을 뒤집는 결정인지** 본다. 뒤집는 것이면 새 파일을 만들고 `supersedes:` 로 옛 결정을 가리킨다. **옛 문서를 고치거나 지우지 않는다** — 무엇을 왜 바꿨는지가 사라진다.

### 2-1. id 를 채번한다

`id` 는 **Notion 태스크가 결정 문서를 가리키는 참조 키**다. 트랙 둘뿐이고 다른 분류축은 만들지 않는다.

| id          | 트랙                      |
| ----------- | ------------------------- |
| `DEC-E-001` | Engineering — 기술 결정   |
| `DEC-P-001` | Planning — 기획·정책 결정 |

**가르는 기준 하나: 사용자에게 보이는 결과가 달라지면 P, 안 달라지면 E.** 삭제 정책은 탈퇴 후 재가입 화면이 달라지므로 P 다. ID 를 UUID 로 할지 auto-increment 로 할지는 사용자가 모르므로 E 다. **애매하면 P 로 보낸다** — 기획이 모르고 지나가는 것보다 낫다.

번호는 **그 트랙의 최대 번호 + 1** 이다. 2번에서 이미 훑은 `docs/decisions/*.md` 의 `id:` 를 모아 정하고, 세 자리로 적는다(`DEC-P-007`). **`id` 가 없는 옛 결정은 소급해 붙이지 않는다** — 앞으로 만드는 것부터다.

### 3. 닿는 문서를 찾는다 — **반영은 따로 묻는다**

**결정과 문서 반영은 별개다.** 결정은 "그때 그렇게 정했다" 는 기록이고, 반영은 "그래서 문서를 이렇게 고친다" 는 다른 작업이다. 정하자마자 문서를 고칠 수 없는 때가 흔하다 — 반영할 문서가 아직 없거나, 노션에 있거나, 다른 결정과 묶어서 한 번에 고쳐야 하거나.

그래서 여기서 하는 일은 **찾아서 보여주는 것까지**다.

`registry.yaml` 로 걸리는 시스템을 잡고, `index.md` 로 그 시스템의 문서를 훑고, 결정에 나온 용어로 `docs/product/` 를 grep 한다. 용어집 표제어도 본다 — 결정이 용어의 뜻을 바꾸는 일이 흔하다.

찾았으면 **목록만** 낸다. 문서 경로 · 어긋나는 절 · red-wiki 소유인지 미러인지. 그리고 한 줄로 묻는다.

> 결정은 남겼습니다. 문서에도 반영할까요?

**결정 카드는 묻기 전에 낸다.** 결정을 남기는 것은 이미 정해진 일이고, 대답을 기다리는 사이에 대화가 끝나면 결정 자체가 사라진다. **두 번 묻지 않는다** — 답이 없으면 결정만 남기고 넘어간다.

반영하지 않기로 해도 아무것도 덧붙이지 않는다. `affects:` 가 어느 문서에 걸리는지 이미 적고 있고, "아직 반영 안 됨" 같은 표시는 반영한 뒤에 아무도 지우지 않아 반드시 거짓말이 된다.

### 3-1. 반영한다고 하면

찾은 문서마다 셋 중 하나를 한다.

| 그 문서가                     | 무엇을                                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| red-wiki 소유(`mirror:` 없음) | **수정 제안 카드를 낸다.** 결정과 어긋나는 절만 고친다                                                           |
| 노션 미러(`mirror: notion`)   | **카드를 내지 않는다.** red-wiki 에서 못 고친다. frontmatter 의 `source` URL 과 **고쳐야 할 절 제목**을 지목한다 |
| 어긋나지 않음                 | 아무것도 안 한다. `affects:` 에만 남긴다                                                                         |

**한 번에 세 장까지 낸다.** 그보다 많으면 목록을 먼저 보여주고 어느 것부터 할지 확인받는다 — 카드 열 장이 한꺼번에 뜨면 아무도 검토하지 않고 전부 저장하거나 전부 닫는다.

**결정 카드를 다시 내지 않는다.** 그건 3번에서 이미 나갔고, 사람이 저장했을 수도 있다. 같은 경로로 또 내면 카드가 둘이 되고 저장은 409 로 막힌다.

**고칠 근거가 결정 하나뿐인 절은 건드리지 않는다.** 결정이 직접 말한 것만 고친다. "이 결정대로면 저기도 이렇게 돼야 하지 않나" 는 추론이고, 그건 `❓확인 필요` 로 남긴다.

### 4. 제안한다

**파일을 직접 쓰지 않는다. 터미널에서 불려 쓰기 도구가 있어도 그렇다.** 아래 블록으로 낸다 — 파일이 생기는 길을 `create-doc`·폼 하나로 유지한다. 그 길이 하나여야 경로·필수값·인덱스 검증이 모든 문서에 똑같이 걸린다.

공통 문법과 파서가 거절하는 조건은 `.claude/rules/proposal-block.md` 에 있다. 아래는 **결정 문서 고유의 frontmatter** 를 얹은 예시다.

````
```red-doc
@path docs/decisions/2026-08-14-auth-token-storage.md
---
id: DEC-E-001
title: 인증 토큰 저장 방식
type: doc
status: 완료
owner: 수빈
decided: 2026-08-14
deciders: [BE리드, 수빈]
affects: [docs/product/general/auth.md]
supersedes: null
from_chat: true # 원천이 대화다. 문서에서 나온 것이 아니다
---

**결정** AT는 FE 메모리, RT는 httpOnly + Secure + SameSite=Lax 쿠키.

**왜** 세션 대비 서버 확장 제약이 적고, 현 인프라에 세션 스토어가 없다.
토큰 탈취 리스크를 RT 하나로 좁히면서 FE 추가 비용이 반나절 수준이다.

**버린 것**

- 둘 다 localStorage — 개인정보 항목을 다루므로 XSS 시 피해 범위가 수용 불가
- 세션 방식 — Redis 신규 도입 필요, 8월 일정 내 인프라 작업 여력 없음
- 둘 다 httpOnly 쿠키 — 도메인 구성이 아직 미확정이라 지금 확정하면 되돌리기 비용이 크다

**누가 언제** BE리드 결정 · 수빈 참여 · 2026-08-14

**영향** 모든 API 호출, CORS 설정. 되돌리기 비용 중간.

**다시 볼 때** 네이티브 앱 클라이언트가 추가될 때 · 세션 스토어를 도입할 때
```
````

- **본문은 굵은 라벨 여섯이다** — 결정 · 왜 · 버린 것 · 누가 언제 · 영향 · 다시 볼 때. 헤딩으로 쓰지 않는다. 결정 문서는 짧아서 헤딩 여섯이 본문보다 길어진다
- 파일명은 `<YYYY-MM-DD>-<영문 kebab-case 요약>.md`. **한 파일에 결정 하나.** 두 개를 묶으면 하나만 뒤집을 때 파일을 쪼개야 한다
- **`id` 를 반드시 넣는다**(2-1). 없으면 카탈로그 검사에 걸리고, Notion 태스크가 이 결정을 가리킬 길이 없어진다
- `status` 는 `완료` 다. 결정은 닫힌 것이라 `작성중` 이 없다
- **`from_chat: true` 를 반드시 넣는다.** 원천이 대화라는 표시이고, 나중에 이 문서를 근거로 쓸 때 `/ask` 가 그 사실을 알린다
- **영향에는 되돌리기 비용**(낮음/중간/높음)을 한 마디로 붙인다. 나중에 뒤집을지 판단하는 자리에서 이것부터 본다

### 5. 끝내고 알린다

- 낸 수정 카드 목록과, **세 장을 넘어 안 낸 나머지**
- 노션에서 고쳐야 하는 것 — 페이지 URL 과 절 제목
- 뒤집은 결정이 있으면 그 경로
- `❓확인 필요` 를 남긴 칸

**안 낸 것을 말하지 않으면 다 된 것으로 읽힌다.** 세 장 제한에 걸려 남은 문서는 반드시 적는다.

## 언제 먼저 물어보나

`CLAUDE.md` 1절의 「결정으로 굳는 말은 그 자리에서 묻는다」 에 있다. **이 스킬은 부를 때만 로드되므로 그 규칙은 여기 살 수 없다** — 부르기 전에 떠야 하는 말이다. 여기 옮겨 적지 않는다. 두 곳에 있으면 한쪽이 낡는다.
