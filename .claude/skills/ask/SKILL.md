# /ask — 근거를 대서 답한다

위키의 값은 "찾을 수 있다"가 아니라 **"이게 현재 기준이다"를 근거와 함께 말해준다**는 것이다.

규칙은 둘로 갈린다. **읽지 않은 것을 말하지 않는다**(정확성), 그리고 **묻지 않은 것을 말하지 않는다**(간결성). 둘 다 지켜야 한다 — 정확하지만 장황한 답은 읽히지 않아서 결국 틀린 답과 같아진다.

## 답의 크기는 질문이 정한다

**이것이 이 스킬에서 가장 자주 어기게 되는 규칙이다.** 근거를 많이 찾았다는 것은 많이 쓰라는 뜻이 아니다.

| 질문 | 답 |
| --- | --- |
| "X가 뭐야" — 정의 | **한두 문장 + 출처.** 그게 전부다 |
| "왜 이렇게 정했어" | 결정 + 이유 + 출처. 세 문장 안 |
| "X 관련 문서 다 찾아줘" | 목록. 이때만 표를 쓴다 |
| "X 어디까지 됐어" | 상태 + 빈 곳 |

찾다가 알게 된 다른 사실은 **답에 섞지 말고 한 줄로 제안한다.** "관련해서 도메인·라이선스 얘기도 있습니다. 볼까요?" 사용자가 원하면 그때 편다.

## 절차

### 1. `index.md` 를 먼저 읽는다

grep 부터 하지 않는다. grep 은 있는 것만 찾고 **없다는 사실은 알려주지 못한다.** 카탈로그는 무엇이 있고 없는지를 한 번에 알려준다.

### 2. `registry.yaml` 로 좁힌다

시스템·도메인이 걸린 질문이면 여기서 경로가 나온다. 여기서 안 나오면 없는 것이다.

**`domains:` 에 걸리는 질문이면 그 도메인 문서(`docs/wiki/domains/<id>.md`)를 먼저 편다.** 특히 **경계·구분**을 묻는 질문이 그렇다 — "A 랑 B 차이가 뭐야" · "이건 어느 영역이야" · "X 도 여기 포함이야". 그 답은 여러 문서에 흩어져 있어서 어느 한 문서를 읽어도 안 나오고, 도메인 문서의 「경계」 절이 그것을 모아 둔 자리다.

**그래도 현재 기준은 `product/` 다.** 위키에서 얻는 것은 *흩어진 것을 모은 구도*이고, 사실 자체의 출처는 그 문서의 `from:` 이 가리키는 원본이다. 답할 때 **원본을 인용한다** — 위키를 인용하면 파생물이 원본 행세를 하기 시작한다. 위키가 원본과 어긋나 보이면 위키가 낡은 것이다(카탈로그가 「원본이 바뀐 파생 문서」로 잡는다).

### 3. 필요한 만큼만 읽는다

**큰 문서를 통째로 읽지 않는다.** 용어집처럼 수십 KB짜리 문서는 grep 이나 부분 읽기로 해당 절만 본다. 정의 한 줄을 찾으려고 16KB를 읽으면 답도 그만큼 부풀어 오른다 — 읽은 것을 쓰고 싶어지기 때문이다.

읽은 파일은 **읽는 즉시 목록에 적는다.**

### 4. 읽은 목록 밖의 경로를 인용하지 않는다

답을 다 쓰고 기억으로 경로를 적으면 없는 파일을 인용하게 된다. 목록은 읽는 시점에 만들어지고, 인용은 그 목록에서만 고른다.

### 5. 답한다

- **같은 사실을 여러 문서가 말하면 한 번만 쓰고 출처를 묶는다.** `— A, B, C`. 같은 정의를 문서마다 반복해 적지 않는다.
- **근거가 없으면 "관련 기록 없음"** 이라고 답한다. 일반 지식으로 메우지 않는다. 메울 거면 "문서에는 없고, 일반적으로는 ~" 이라고 출처를 분리한다.
- 문서끼리 **어긋나면 양쪽을 다 보여주고** 어느 쪽이 최신인지 판단 근거를 댄다(`updated`, `<문서>.history.yaml`, `authoritative`). 한쪽을 조용히 고르지 않는다.
- **현재 기준은 제품 문서에서 읽는다.** `docs/decisions/` 는 "왜 · 언제 · 누가" 를 답하는 자리지 "지금 무엇이 기준인가" 를 답하는 자리가 아니다. "X 가 어떻게 되어 있어" 는 `product/` 로 답하고, "왜 그렇게 했어" 는 결정으로 답한다.
- **결정과 제품 문서가 어긋나면 반영이 안 된 것이다.** 한쪽을 조용히 고르지 않는다 — **"결정은 X(정한 날 …), 문서는 아직 Y 입니다"** 로 둘 다 보여준다. 결정이 최신이라고 해서 문서가 틀렸다고 단정하지 않는다. 반영을 미룬 것일 수도, 반영하지 않기로 한 것일 수도 있다.
- **결정을 인용하기 전에 뒤집혔는지 본다.** `index.md` 의 Decisions 표가 `뒤집힘 → <새 결정>` 을 표시한다. 뒤집힌 결정은 근거로 쓰지 않는다. 그것을 콕 집어 물었을 때만 답하고, **뒤집혔다는 사실과 지금 기준을 같이 적는다.**

### 6. 경고는 답에 영향을 줄 때만 단다

`generated: true` · `from_chat: true` · `mirror: notion` · `❓확인 필요` 는 **그 답의 신뢰도에 직접 걸릴 때만** 알린다.

- 판단 근거로 쓴 문장이 `generated: true` 문서에서 왔다 → 알린다
- 판단 근거로 쓴 문장이 `from_chat: true` 문서(결정)에서 왔다 → **"대화에서 나온 결정입니다"** 라고 알린다. 문서에서 나온 사실과 대화에서 나온 사실은 무게가 다르다
- 답한 내용에 `❓` 가 걸려 있다 → 알린다
- 그 문서에 `❓` 가 있지만 **다른 절 얘기다** → 알리지 않는다
- 미러 문서라는 사실은 **고치라는 요청이 나올 때만** 알린다

매번 붙이면 아무도 안 읽는다.

### 7. 답을 위키에 남기는 것은 기본이 아니다

**답을 문서로 저장하자고 먼저 제안하지 않는다.** 사용자가 요청할 때만 한다.

저장하면 위키가 스스로를 인용하기 시작한다 — 한 번 들어간 답이 그다음부터 근거가 되고, 틀렸어도 아무도 다시 확인하지 않는다. 근거였던 원문은 그대로 있는데 요약본이 옆에 하나 더 생기는 것이라, 얻는 것보다 갈라지는 위험이 크다.

요청받아 남길 때는 `red-doc` 제안으로 내고(아래 절), frontmatter 에 **셋을 반드시 넣는다.**

```yaml
generated: true # AI 가 쓴 문서다. 사람이 검토하면 지운다
from: [실제로 읽은 문서 경로, ...] # 필수 — 비면 지어낸 것이다
asked: "<원래 질문 그대로>" # 어떤 물음의 답인지. 나중에 맥락 없이 읽히지 않게
```

`generated: true` 는 표시가 아니라 **경계**다. 이 표시가 붙은 문서를 다음 답의 근거로 쓸 때는 반드시 알린다(6절).

## 문서를 써 달라고 하면

**여기서는 파일을 만들 수 없다.** 도구가 `Read`·`Glob`·`Grep` 뿐이고, **사용자가 허용해 줄 방법도 없다** — 이 채팅에는 권한을 묻는 자리 자체가 없다.

그래서 **"권한을 허용해 주시면 저장하겠습니다" 라고 답하지 않는다.** 사용자가 할 수 없는 일을 시키는 것이고, 다 만들어 놓고 못 받는 상태로 대화가 끝난다.

대신 **제안한다.** `red-doc` 블록을 낸다 — 뷰어가 **검토 카드**로 그리고, [폼에서 열기] 를 누르면 만들기 폼이 채워진 채 열린다. 저장은 사람이 한다.

**문법은 `.claude/rules/proposal-block.md` 가 정한다. 블록을 내기 전에 읽는다.**

절차 전체 — 어디에 넣을지 고르는 법, 고칠 문서를 먼저 읽는 규칙, 제안하지 않는 것(`_sources/` · 미러 · 화면정의서) — 는 `/draft` 스킬에 있다. 문서 작성이 요청의 본론이면 그쪽으로 답한다.

## 하지 않는 것

- **파일을 만들거나 고치지 않는다.** 읽기 전용이다. 쓰기를 시도하지도, 권한을 요청하지도 않는다 — 위의 제안 블록으로 낸다.
- **묻지 않은 것을 표로 만들지 않는다.** 표는 사용자가 목록을 요청했을 때만.
- **같은 정의를 출처별로 반복하지 않는다.**
- **"아마" · "보통은" · "일반적으로" 로 문서의 공백을 메우지 않는다.**
- **답을 근거보다 길게 쓰지 않는다.** 문서 한 줄에서 문단 세 개를 만들면 그게 지어낸 것이다.

## 예시

### 정의 질문 — 이렇게 답한다

```
사용자: red 에서 정의하는 IASM이 뭐임

읽음: index.md, registry.yaml, docs/product/general/glossary.md#A-3

답: 회사 내부망에서 공격 표면을 발견·평가·축소하고 지속적으로 모니터링하는
    시스템입니다. 업계 표준 분류로는 CAASM 에 해당합니다.
    — glossary.md, registry.yaml, product/systems/overview.md (같은 정의)

    기능명세는 아직 없습니다 — registry 의 engine_spec·platform_spec 이 둘 다 null 입니다.

    관련해서 도메인(공격 표면·자산 관리·취약점 인텔리전스)과 라이선스 단위 얘기도
    용어집에 있습니다. 볼까요?
```

### 같은 질문 — 이렇게 답하면 안 된다

- 같은 정의를 glossary · overview · registry 각각 인용해 세 번 적는 것
- 묻지도 않은 도메인 · 표기 · 센서 · 라이선스를 4행 표로 펴는 것
- 답보다 긴 "주의할 점" 절을 붙이는 것
- IASM 정의와 무관한 `❓` (솔루션이 4가지냐 3가지냐) 를 끌어오는 것
- 미러 문서라는 고지를 고치라는 요청도 없는데 붙이는 것

### 경계 질문 — 도메인 문서를 먼저 편다

```
사용자: Finding 이랑 Vulnerability 가 뭐가 달라?

읽음: index.md, registry.yaml, docs/wiki/domains/vulnerability-intelligence.md,
      docs/product/general/glossary.md#내부-소통-용어

답: Finding 은 점검·스캔·침투테스트에서 나온 **넓은 의미의** 취약점입니다 —
    CVE·CWE·CCE·정보 노출·정책 위반·단순 참고사항까지 포함합니다.
    Vulnerability 는 그중 **실제 악용 가능한** 것입니다(예: CVE).
    — glossary.md 「내부 소통 용어」

    플랫폼 지표인 `CVE 건수` 도 이 둘과 또 다른 말입니다.
```

용어집의 두 행이 표에서 떨어져 있어 **따로 읽으면 "다르다"는 사실 자체가 안 보인다.** 도메인 문서가 그것을 붙여 둔 자리다. 다만 **인용은 용어집**이다 — 위키는 찾아가는 길이지 출처가 아니다.

### 없을 때

```
사용자: AI DAST 가 인증 걸린 페이지도 점검해?

읽음: index.md, registry.yaml, docs/product/systems/overview.md

답: 관련 기록 없음. AI DAST 는 "웹앱을 실제로 돌려보며 AI 가 취약점을 찾아낸다"
    까지만 적혀 있고 인증 처리는 문서에 없습니다.
    — product/systems/overview.md

    들어올 자리는 docs/product/systems/ai-dast/ 인데 지금 비어 있습니다.
```

없다고 답하는 것이 정상 동작이다. 문서가 비어 있다는 사실 자체가 정보다.
