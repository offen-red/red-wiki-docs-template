# 문서를 어디에 두고 어떻게 쓰나

먼저 CLAUDE.md 2절로 걸러낸다(red-wiki 소관인가?). 통과하면 아래를 따른다.

## 존 고르기

| 존         | 답하는 질문             | 소유 | 판별                                                       |
| ---------- | ----------------------- | ---- | ---------------------------------------------------------- |
| `product/` | red가 무엇을 하나       | 사람 | 원천이나 사람 머리에서만 나오는 것                         |
| `wiki/`    | 이 개념·용어가 뭐였지   | LLM  | **지워도 `_sources/`·`product/` 에서 다시 만들 수 있는 것** |
| `ops/`     | 이 위키를 어떻게 굴리나 | 사람 | red-wiki 자체에 대한 규칙                                  |
| `decisions/` | 왜 그렇게 정했나      | 사람 | **원천 파일이 없다.** 대화·회의에서만 나온다 (`/decision`) |

애매하면 **"이 페이지를 지워도 원천·`product/` 에서 다시 만들어낼 수 있나?"** — 예면 `wiki/`, 아니면 `product/`.

## 존 안에서 어느 폴더인가

| 폴더                                 | 다루는 것                                                          | 유형      |
| ------------------------------------ | ------------------------------------------------------------------ | --------- |
| `product/`                           | 제품 전체 한 장                                                    | hub       |
| `product/systems/<시스템>/`          | 그 시스템의 기능명세. **개요는 두지 않고 하위 폴더 없이 평평하게** | doc       |
| `product/general/`                    | 시스템들이 공유하는 규칙·문구                                      | hub · doc |
| `product/screens/<시스템>/<화면ID>/` | 화면정의서 + 목업 + 이력                                           | screen    |
| `ops/`                               | red-wiki 자신을 굴리는 규칙·절차                                   | guide     |
| `wiki/`                              | 파생 — 용어·도메인                                                 | AI 생성   |
| `decisions/`                         | 결정 하나에 파일 하나. `<날짜>-<요약>.md`                          | doc       |

**`guide` 는 전부 `ops/` 다.** 규칙·절차는 red-wiki 를 굴리는 방법이지 제품 지식이 아니다. `product/screens/` 에는 화면정의서 본체만 둔다(올리는 절차는 `docs/ops/tooling/screens.md`).

새 폴더는 `product/` · `product/general/` · `ops/` 아래에만 만든다. `decisions/` 는 평평하게 둔다 — 결정을 분류하기 시작하면 어느 칸에 넣을지부터 논의하게 된다.

**`decisions/` 는 지우지도 고치지도 않는다.** 뒤집힌 결정도 남긴다 — 무엇을 왜 바꿨는지가 거기 있다. 뒤집을 때는 새 파일을 만들고 `supersedes:` 로 옛것을 가리킨다.

**`overview.md` 는 큰 폴더(존)에만 둔다** — `product/` · `product/systems/` · `product/general/` · `product/screens/` · `ops/` · `wiki/`. 개별 시스템·개별 화면 폴더에는 두지 않는다. 개요는 **거기서만 알 수 있는 것**(결정·판별 기준·제외 범위)을 적을 때 두는 것이고, "이 폴더는 무엇을 담는다"는 `index.md` 카탈로그가 이미 자동으로 만든다. 목록만 적은 개요는 같은 사실을 두 곳에 두는 일이라 반드시 한쪽이 낡는다 — 세 시스템 설명이 네 곳에 복사돼 넷 다 틀렸던 적이 있다.

여기서 나오는 규칙 둘.

1. **`wiki/` 는 사람이 직접 편집하지 않는다.** 틀린 게 있으면 원본(`_sources/` 또는 `product/`)을 고치고 `/rebuild-wiki` 로 다시 생성한다.
2. **`product/` 는 사실을 복제하지 않고 `wiki/` 를 링크한다.** 용어·엔티티 정의는 한 곳에만 둔다(drift 방지).

## 새 문서 vs 기존 수정

- **새 문서**: 독립적이고 링크 가능한 대상(새 시스템·기능·화면).
- **기존 수정**: 이미 있는 대상의 속성·업데이트.
- 새로 만들면 frontmatter `title` 을 반드시 채운다 — 그것이 사이드바에 보이는 이름이다. 등록 작업은 없다(사이드바는 폴더 구조 그대로다).

## 원천 — `docs/_sources/`

**이미지만 들어간다.** 문서에 붙는 스크린샷·다이어그램, 그리고 노션 동기화가 미러와 함께 받아 온 이미지다. 엑셀·정의서 같은 문서형 원천은 **넣지 않는다** — 원본은 노션·OneDrive 에 두고 `registry.yaml` 의 `origin:`·`url:` 로 가리킨다.

- 넣는 것은 **사람이 앱의 편집 폼에 끌어 놓는다.** 그러면 앱이 그 문서의 원천 폴더(`docs/_sources/<문서 경로의 / 를 - 로>/`)에 넣고 본문에 경로를 적는다. **폴더를 손으로 만들지 않는다.**
- AI 는 `_sources/` 에 파일을 만들지 않는다. 제안 블록도 그 경로를 거절한다(`.claude/rules/proposal-block.md`).
- 원천이 늘었다고 문서가 저절로 생기지 않는다. 본문을 쓰는 것은 `/draft` 다.

**10개 넘는 문서를 건드릴 것 같으면 고치기 전에 범위를 먼저 알리고 확인받는다.** 한 번에 대량으로 고치면 사람이 검토할 수 없고, 검토되지 않은 변경은 위키를 썩게 한다. (`docs/wiki/` 는 예외다 — 재생성 가능한 층이라 `/rebuild-wiki` 가 확인 없이 돈다.)

## Query — 질문에 답할 때 (읽기 전용)

`/ask` 스킬을 쓴다. 요점은 **`index.md` 부터 읽고, 근거 문서를 인용해 답하고, 없으면 "관련 기록 없음"** 이다. 지어내지 않는다.
